# Aim benchmark suite

A small, reproducible HTTP benchmark that compares five Dart HTTP setups —
`dart:io` alone, `aim`, `shelf` + `shelf_router`, `relic`, and `dart_frog` —
on the same four request scenarios, on one machine, one at a time.

## What this measures

Every app answers the same four scenarios with the same status code and
body. All five apps are `dart compile exe` binaries (ahead-of-time
compiled), run as a single isolate, add no middleware (no logging, no
compression, nothing beyond what the framework does by default), keep
their framework's default configuration, and read their port from the
`PORT` environment variable.

| Scenario | Request | Response | What it exercises |
|---|---|---|---|
| `plaintext` | `GET /` | `Hello, World!` (text) | Baseline request/response overhead with no parsing. |
| `params_json` | `GET /users/42?name=aim` | `{"id":"42","name":"aim"}` (JSON) | Path parameter extraction, query string parsing, JSON encoding. |
| `post_json` | `POST /json` with a JSON body | the same JSON, echoed back | Request body reading and JSON decoding, on top of encoding. |
| `routes_100` | `GET /r/item100` | `item100` (text) | Router lookup cost with 100 registered static routes (`/r/item1` … `/r/item100`) instead of one. |

## What this does not measure

This suite does not cover TLS termination, database or other I/O-bound
work, real network conditions (it always runs against `127.0.0.1`),
multiple isolates, or large request/response bodies. It measures
in-process HTTP handling only. The three main scenarios mirror the shape
of comparable HTTP framework benchmarks elsewhere in the Dart and JS
ecosystems (a plaintext route, a route with a path parameter and a query
string, and a JSON echo route); the fourth scenario, `routes_100`, adds a
router-scaling check that those benchmarks don't have.

## Apps

| App | Directory | Notes |
|---|---|---|
| `dart_io` | `bench/apps/dart_io` | `dart:io`'s `HttpServer` with manual routing, no framework. |
| `aim` | `bench/apps/aim` | `package:aim_server`. |
| `shelf_router` | `bench/apps/shelf_router` | `package:shelf` + `package:shelf_router`. |
| `relic` | `bench/apps/relic` | `package:relic` (a re-export of `relic_core` and `relic_io`). |
| `dart_frog` | `bench/apps/dart_frog` | File-based routing; see below. |

Each app directory has its own `pubspec.lock`, committed to the repository
so the exact package versions a set of results was measured against are
pinned and reproducible.

`dart_frog` routes are files under `bench/apps/dart_frog/routes/`, so the
100 routes for the `routes_100` scenario are generated rather than
hand-written: `bench/apps/dart_frog/tool/gen_routes.dart` (re)writes
`routes/r/item1.dart` … `routes/r/item100.dart`. Run it from the app
directory with `dart run tool/gen_routes.dart` after changing `routeCount`.

`dart_frog`'s production server is generated by `dart_frog_cli` (`dart run
dart_frog_cli:dart_frog build`, which the runner runs as a prebuild step)
and that generated server binds `InternetAddress.anyIPv6` — all interfaces,
dual-stack — instead of loopback only. The other four apps bind
`127.0.0.1` directly in their own `bin/server.dart`. This suite keeps each
framework's own default rather than patching it, so that difference is
left as is; it has no effect on the results because the load generator
always connects to `127.0.0.1`.

## Prerequisites

- Dart 3.13 or newer.
- [`oha`](https://github.com/hatoo/oha) 1.16 or newer: `brew install oha`.
- macOS. The runner reads machine info with `sysctl` and `sw_vers`, and
  reads a running app's memory with `ps` (see "Reading the numbers").

## Run

```bash
cd bench/runner
dart pub get
dart run bin/bench.dart verify        # every app must answer identically
dart run bin/bench.dart run --label <machine-name>
dart run bin/bench.dart render ../results/<date>-<label>.json
```

`verify` builds every app and checks it answers all four scenarios exactly
as defined in `bench/runner/lib/scenarios.dart`; it does not run any load.

`run` builds, verifies and measures every app in turn, then writes
`bench/results/<date>-<label>.json` and prints the same tables that
`render` would produce from that file.

`render` re-prints an existing results JSON file as Markdown tables,
without rebuilding or re-running anything.

Options, with their defaults:

| Command | Option | Default | Meaning |
|---|---|---|---|
| `verify`, `run` | `--only <name>` | all apps | Restrict to one app (`dart_io`, `aim`, `shelf_router`, `relic`, or `dart_frog`). |
| `run` | `--label <name>` | `local` | Suffix of the results file name. |
| `run` | `--duration <seconds>` | `10` | Seconds `oha` runs per measured run. |
| `run` | `--connections <n>` | `64` | Concurrent connections `oha` opens. |
| `run` | `--runs <n>` | `5` | Measured runs per scenario; the median is kept. |
| `run` | `--warmup <seconds>` | `3` | Seconds of discarded warmup load per scenario, before the measured runs. |

Every app is started on port `18080`.

## Fairness rules

- All apps are measured on the same machine, in the same run, with the
  same Dart SDK and the same `oha` binary.
- Every app is compiled the same way (`dart compile exe`, AOT) and run the
  same way (single isolate, no middleware).
- Apps are measured one at a time, never concurrently, with a pause
  between apps and between runs so one app's leftover load cannot bleed
  into the next measurement.
- Every scenario uses the same warmup duration and the same number of
  measured runs for every app.
- `verify` checks every app against every scenario and prints each
  mismatch it finds, but keeps going on to the next app. `run` treats an
  app the same way once it starts measuring it: an app that does not
  answer every scenario with the exact status code and body defined in
  `scenarios.dart`, or whose success rate drops below 100% under load, is
  skipped rather than measured — `run` moves on to the next app instead of
  stopping. A skipped app is recorded under `skipped` in the results JSON
  (name and reason) and listed in a "Not measured" section of the
  rendered table, never with fabricated numbers. The results file is
  still written for every app that was measured, and `run` exits with a
  non-zero status when anything was skipped, so a skipped app is never
  silently missing.
- The machine should be plugged in, otherwise idle (no other load-bearing
  processes, no browser windows open) for the duration of a `run`.
- Every results file and rendered table records the date, the machine's
  hardware and OS, the Dart and `oha` versions, and the settings the run
  used, so a set of numbers is never read without its context.

## Reading the numbers

Each scenario's table reports requests/s, p50 and p99 latency; each is the
median across the measured runs (`--runs`, default 5), after a discarded
warmup (`--warmup`). Startup time is measured from process spawn to the
first successful `200` response on `/`. Memory is read once, immediately
after the load runs finish, from the still-running process — it is not a
peak or an average over the run.

Memory is reported as a physical footprint, not strictly RSS: recent
macOS versions refuse the `rss` column to unentitled callers of `ps`, so
the runner reads `ps -o rss=` where the OS allows it and otherwise falls
back to parsing `footprint <pid>`'s physical footprint line. The rendered
table's memory column is labelled "Memory after load (MiB)" rather than
"RSS" to reflect that.

A results file is a snapshot of one machine at one point in time. It is
not a claim about any other machine, Dart version, or package version,
and it is not a ranking: read the numbers in a results file or a rendered
table for what they say, not as an ordering of the apps.

## Adding an app

1. Create `bench/apps/<name>/` with its own `pubspec.yaml` and a
   `bin/server.dart` (or, for a file-routing framework, the equivalent
   entry point) that implements all four scenarios in
   `bench/runner/lib/scenarios.dart`: `GET /`, `GET /users/:id` reading
   both the path parameter and the `name` query parameter, `POST /json`
   echoing the request body, and the `routeCount` (100) static routes
   `/r/item1` … `/r/item100`. It must read its port from the `PORT`
   environment variable and bind to `127.0.0.1`.
2. Add an `AppSpec` for it in `bench/runner/lib/apps.dart` — name,
   directory, entry point, any prebuild steps, and the packages whose
   locked versions should be recorded with the results.
3. Run `dart pub get` in the new app's directory and commit the resulting
   `pubspec.lock`. Root `.gitignore` ignores `pubspec.lock` in general, but
   `!/bench/apps/*/pubspec.lock` un-ignores it for every app directory
   under `bench/apps/`, so a new app's lock file is picked up the same way
   the existing ones are; it still has to be `git add`ed explicitly.
4. Run `dart run bin/bench.dart verify --only <name>` from `bench/runner`
   until it reports `ok`.
